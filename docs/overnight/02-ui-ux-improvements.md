# Workstream 2 — UI/UX Improvement Pass

Reviewed as Admin, Manager, and Employee across every dashboard, table, form, and modal.
This is a mature, already-polished UI (consistent skeletons, toasts, badges, empty states
in almost every table checked) — findings below are the genuine gaps found, not a general
redesign wishlist.

## HIGH Priority

| Screen/Component | Problem | Improvement | Why it's better | Status | Priority |
|---|---|---|---|---|---|
| Employee sidebar (`Layout.jsx`) | The "coming soon" placeholder list showed a disabled "Active Timer" nav item, while a fully working live timer widget (Play/Pause/Stop) already renders lower in the same sidebar. | Removed the placeholder. | A feature that already works should never be advertised as "coming soon" in the same view — it undermines trust and confuses users into thinking the timer isn't real yet. | FIXED | HIGH |
| Manager sidebar (`Layout.jsx`) | The placeholder list showed a disabled "Team Reports" item, while managers already get an equivalent Task→Time→Capacity→Completion→Deadline→Quality→Pattern breakdown per employee on their Overview page (`TeamSignalsPanel`, `AttentionZone`). | Removed the placeholder. | Same as above — tells managers a capability doesn't exist when a close equivalent is one scroll away. | FIXED | HIGH |
| Approve action styling (`ApprovalGatingPanel.jsx` vs `PendingReviewQueue.jsx`) | The identical "Approve" action (moving an In Review task to Completed) was a plain primary-color button in the task detail modal, but a custom solid-green button in the manager's Pending Review queue — same business action, two different visual treatments. | Made `ApprovalGatingPanel`'s Approve button use the same green treatment as the queue's. | The same workflow action should look identical everywhere it appears — inconsistent color-coding on approve/reject undermines the "green = go, red = stop" convention the rest of the app relies on. | FIXED | HIGH |
| Task status change control (`TaskListView.jsx`, `TaskKanbanBoard.jsx`, `TeamTasksTable.jsx`) | The single most-used control on every task row — the inline status-transition dropdown — was a raw, manually-styled native HTML `<select>`, while every other dropdown in the app (Category, Priority, Assignee, Department, Role, Reports timeframe) uses the themed shadcn `Select` component. | Swapped all three to the themed `Select`/`SelectTrigger`/`SelectContent`/`SelectItem` pattern, sized to match each context (compact `h-8`/`h-7` triggers). Verified live in a real browser (Playwright driving the actual running app, logged in as employee/manager/admin): status changes fire correctly, the popover isn't clipped in the dense table rows or Kanban cards, and clicking the dropdown no longer opens the task detail modal underneath it (row click-through still correctly suppressed). | Now visually and behaviorally consistent with every other dropdown in the app, with confirmed no regression to the existing click-handling logic. | FIXED | HIGH |
